# API de la ampliación comercial 0.4.0

Complementa `API_Y_ARQUITECTURA.md`. Todas las rutas de esta tabla requieren sesión Bearer. Las comprobaciones de propietario y rol se ejecutan en los servicios.

| Método y ruta `/api` | Acceso | Resultado |
|---|---|---|
| `GET /clients` | Asesor: propios; responsables: todos | Clientes activos y sus operaciones autorizadas |
| `GET /clients/{id}` | Propietario o responsable | Ficha, cotitular y lotes de sus operaciones |
| `PUT /clients/{id}` | Propietario o responsable | Actualización y vínculo de cotitular |
| `DELETE /clients/{id}` | Propietario o responsable | Retiro del registro activo con historial conservado |
| `DELETE /clients/{id}/cotitular` | Propietario o responsable | Desvinculación para futuras operaciones |
| `GET /reservations` | Propias o todas según rol | Operaciones incluidas ventas, con condiciones guardadas |
| `GET /operations/{id}` | Asesor asignado o responsable | Datos acordados, venta, catálogo actual e historial |
| `PUT /operations/{id}` | Responsable comercial o administrador | Corrección versionada, con motivo y auditoría |
| `GET /operations/{id}/share` | Responsable comercial o administrador | Datos y referencias de fotografías para compartir |
| `GET /operations/{id}/documents/{doc}` | Responsable comercial o administrador | Fotografía conservada en esa operación |
| `GET /admin/users` | Responsable comercial o administrador | Usuarios sin hashes de contraseñas |
| `POST /admin/users` | Administrador | Alta de cuenta |
| `PUT /admin/users/{id}` | Administrador | Modificación de cuenta y revocación de sesiones |
| `PATCH /admin/users/{id}/active` | Admin: habilitar/deshabilitar; comercial: deshabilitar | Cambio de acceso y revocación |
| `DELETE /admin/users/{id}` | Administrador | Cuenta retirada, referencias históricas conservadas |
| `GET /admin/catalog` | Administrador | Catálogo con identificadores y versiones |
| `POST /admin/catalog/preview` | Administrador | Multipart `file`; normalización y vista previa |
| `POST /admin/catalog/apply` | Administrador | JSON `rows` y `motivo`; aplicación transaccional |
| `GET /admin/history?entity=OPERACION` | Responsable comercial o administrador | Hasta 500 cambios por tipo; admite CLIENTE, OPERACION, CATALOGO, USUARIO |
| `GET /notifications` | Cualquier usuario activo | Avisos generales y contador individual |
| `POST /notifications/read` | Cualquier usuario activo | Marca avisos recibidos hasta el ID `hasta` |
| `POST /notifications/{id}/read` | Cualquier usuario activo | Marca un aviso individual |

`POST /reservations` conserva los campos anteriores y añade `precio_acordado`, `inicial_acordada`, `numero_cuotas_acordado` y `version_catalogo`. Un asesor no puede enviar un precio distinto del catálogo vigente. El servidor calcula y guarda la mensualidad; no confía en una mensualidad enviada por el cliente HTTP.

`POST /reservations/{id}/sale` admite `numero_cuotas` y acepta el plan originalmente aprobado aunque se publique un catálogo posterior. Las condiciones definitivas pertenecen a la venta, no al catálogo.

La corrección requiere `version`, `precio`, `inicial`, `numero_cuotas`, `monto` y `motivo`. Admite `observacion`, `cliente_id`, `cotitular_id`, `quitar_cotitular`, `asesor_id`, `fecha` y `actualizar_personas`. Los datos y documentos históricos se conservan por defecto. La actualización desde fichas actuales es explícita y se audita.

Una importación o corrección con versión desactualizada responde 409. Los errores de datos responden 400, las operaciones fuera del rol 403 y los registros inexistentes 404. Un lote que esté vendido al aplicar una importación se omite y se informa en el resultado.

Los avisos se insertan dentro de la transacción comercial. El cliente los consulta cada 15 segundos; el detalle de una operación ajena no se incluye en el enlace del aviso del asesor. No se envían push fuera de la aplicación sin configurar un proveedor.
